## 哪些可以少传

**对当前明确的离线纯文本任务：**

- 用一次简短验收约束替代完整 Goal 中重复的任务说明。保留字段/风格/事实要求，移除仅供数据库阶段使用的价格、封面、排序和状态。
- 原始 before 可移出模型上下文，前提是正向事实已经完整、原始问题可用明确检查清单表达。若原文有尚未归入事实表的重要信息，不能直接删。
- Plan 无新增验收信息时不再传其完整叙述；本例 Skill 选择与基础工具授权由代码控制，相关模板不需反复让 Reflector 阅读。
- 将原始答案和片段列表合并成一份按字段、句子分组的候选内容，保留 13 个 ID 和覆盖要求。不要用字符偏移让模型猜上下文，也不要只返回少数错误 ID、默认其余都检查通过。
- 通用副作用检查示例换成按任务范围选择的短规则。本例没有文件/数据库交付要求；一般写入任务仍必须保留相关规则与证据，不能因为本轮工具数为 0 就删掉。
- 输出也能省：现在模型在 reason、planAdjustment 和逐项检查中重复问题，框架随后又重建理由/提示。可保留简短总体原因及逐项结果，避免长篇重复，但不能牺牲覆盖与有用解释。

不建议把完整 Skill 正文、全部会话历史或工具输出一股脑加入反思。当前 Skill 中的 SQL 写库、批量推进和相关 Skill 等段落不适用于此任务；应提供经过确认的任务相关验收规则。

## 当前不准确的关键原因

1. **规则边界不清。** 新说明禁止将通用知识当额外证据，同时允许解释能力含义；没有明确区分“教学演示→课堂教学场景”的范围内转述、“拖拽示教→手动引导示教”的含义解释，与“无需复杂编程、低门槛”等新增产品性质。模型容易退化为词面匹配。应该明确：常识可用于理解术语，不可用于凭空确立产品属性；边界不明应待复核。
2. **逗号片段缺显式关联。** “操作者可以……”与前文“它支持拖拽示教”分成独立 ID，片段没有 field/sentence 关系。虽然完整答案仍在前面，复核时还要自行恢复关联。应按原句/字段分组保留语义，而非继续更细切碎。
3. **UNCERTAIN 被当作确定错误。** FactualGrounding.enforce 将不确定与不支持合并为 UNSUPPORTED_CLAIMS，并在 CONTINUE 路径（包括被否决的 FINISH）生成同类删除/改写提示。合理解释不确定时，会被当成必须删除。应区分确定错误和需要补证/人工复核，均不直接 FINISH，但不强制相同修正动作。
4. **覆盖了模型原始提示。** 本次模型总体理由/修改提示聚焦若干新增产品性质，checks 却额外拒绝用途转述与能力解释；框架以全部问题片段重建 reason/hintForNext，进一步丢失原有层次。原文只保存在原始事件/Trace，后续规划看到的是被重写的提示。建议分别保存模型提议与框架验证结果，只合并确定的修改事项。

因此下一步应先修判断边界与反馈处理，再优化材料布局；不能仅靠删提示词来解决准确性。

## 哪些信息值得补齐

| 信息 | 当前状况 | 建议 |
|---|---|---|
| 正向事实 | 本例已经完整提供 | 保留，继续与旧文本/候选答案明确分离 |
| 允许的转述/解释及禁止扩展的边界 | 有笼统规则，缺少稳定区分 | 用明确政策和独立校准例子说明，不把本题参考答案喂给反思器 |
| 与本任务相关的验收清单 | 依赖 Goal/Plan 转述 | 明确提供短清单；不需要整个 Skill |
| 本地格式/禁词检查 | Runner 在反思后执行 | 若前移，应以有范围说明的结果传入，不能用一个“通过”暗示事实已验证 |
| 字段/句子归属 | 当前片段只有编号 | 补组关系，候选只保留一份 |
| finalAnswerRequirements | Executor 使用，Reflector 未显式传入 | 相关时加入检查清单并标明来自计划，不能覆盖用户原始要求 |

还有几项属于通用框架问题，不是本次误报的直接原因：

- Reflector 仅传本轮工具记录。priorSteps 目前只参与硬 guard 判断，没有把相关历史操作证据送进提示词；多轮任务可能把先前已完成的写入误判为没做。应选择相关已验证记录，不能拿 Planner 的概述或模型总结当作证据。
- Reflector 没有工具来读取“完整输出保存在某文件”的指针。若观察已截断，指针本身不能证明结果；应由框架提供关键结果/验证摘要，并标明完整性，必要时补充证据后再判断，而非盲传所有原文或假定模型能自行读取。
- 会话约束可能被 TaskPlanner 拼入 narrative，项目规则/结构化验收没有单独可靠入口。全局删除 Plan 会有丢失约束风险，应先提取必要验收信息。
- TaskRequest.inputs 在三个 worker 中没有显式读取。P07 把结构化包编码进 Goal 避开了此问题，通用 API 调用不能因为字段存在就假定反思器已看到。

## 推荐顺序

1. 先校准等义转述/术语解释与新增性质的边界，区分 UNCERTAIN 的处理，并保留模型原理由。
2. 再对离线任务去重 Goal/Plan，使用一份分组候选；确定性规则检查尽量本地完成，保留全部权威事实及关键验收要求。
3. 用旧坏答、合格参考、正常转述/术语解释，以及“同一词语有明确事实依据”的小校准集验证，防止变成词语黑名单；随后才测 Token 变化。每次只改一个主要因素。
