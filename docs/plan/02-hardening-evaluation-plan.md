## 1. 固定模型与配置

执行、规划、反思统一为官方 `deepseek-flash`，通过 `https://api.deepseek.com/v1/chat/completions` 调用，引用 `${DEEPSEEK_KEY}`。可选 Judge 也改为同一官方 Flash；本次新增用例不用 Judge。

官方目前推荐模型名为 `deepseek-flash`，旧 `deepseek-v4-flash` 是兼容名称，见 [DeepSeek 官方说明](https://api-docs.deepseek.com/zh-cn/)。不再通过模型池别名，以减少不同请求落到不同模型的干扰。

本地 `~/.rex/config.yml` 修改前备份，其他配置保持原样；评测使用仓库独立配置和最新本地 JAR。评测进程移除 `REX_MODEL` / `REX_API_KEY` 覆盖，防止污染固定配置。Key 不写入数据集或仓库。

### 确定性回归重点

- 无输出与持续输出都能触发截止时间；部分输出保留，已发现子进程停止，中断标志恢复。
- 已存在/不存在路径的 `../`、外部符号链接、损坏/循环链接、链接后 `..` 都受校验。
- 正常内部链接、多目录与新建文件不受误伤。
- 确认后目标被替换时拒绝写入，原目标不变。
- 授权按会话 UUID 隔离，重建保留，同一进程切回恢复；重启不继承。

### 真实模型重点

每例明确要求使用指定工具，并在评分时检查实际工具输出，防止模型直接拒绝、没有执行工具也被算作边界修复成功。

超时用例运行受控的 `sleep 45` 或输出循环，期望约 30 秒返回超时。路径用例的外部文件位于测试框架自己的 `outside/`，只包含合成标记。正常用例覆盖合法链接编辑、新建多级文件和跨轮读取递增。

### 人工交互重点

管道模式关闭确认，无法验证 `always` 或真实终端信号，因此不把这类结果归入模型用例通过率。会话授权持久化尚未实现：重启后重新确认是当前预期，新需求见 [11 月 TODO](2026-11-todo.md)。

## 3. 执行顺序

1. 准备：离线校验定义、夹具和评分器；导入 Opik 后回读计数。不调用模型、不创建实验分数。
2. 基础验证：确认 Opik 后端与 ClickHouse 正常，构建当前 JAR，运行 Java 回归。
3. 单例冒烟：仅执行 `smoke-utf8`，核对官方模型、Trace 完结、真实 `bash` Span、输出与评分。链路未通过时不扩大规模。
4. 低耗时用例：执行非零退出、正常文件、多轮任务，观察工具选择与实际文件结果。
5. 边界与超时：执行 5 个路径用例和 2 个超时用例，检查拒绝发生在哪一层、是否有绕过重试、子进程是否残留。
6. 人工交互：验收 4 个终端场景，记录会话切换与暂停/恢复表现。
7. 复盘：将失败分为工具缺陷、模型决策、任务编排、观察链路四类，再决定修复与针对性重测。

执行命令见 [评测 README](../../evals/README.md)。用户后续授权完整评测后已完成全部阶段；原定 4 项人工场景通过真实 PTY 自动验收。原始通过率与新发现的输入保真问题分别记录，不混为无缺陷结论。

## 4. 观察指标

| 维度 | 观察内容 |
|---|---|
| 正确性 | 实际文件结果、最终回答、任务状态、错误报告是否一致 |
| 执行证据 | 指定工具是否调用、参数是否符合请求、真实输出与 Trace 是否完整 |
| 边界 | 合成外部文件是否泄漏或被修改，拒绝后是否尝试其他绕过路径 |
| Shell | 工具耗时、超时原因、部分输出、取消后进程状态 |
| 授权 | 跨会话隔离、同会话重建与切回、重启语义、提示准确性 |
| 成本与延迟 | 任务总耗时、工具 Span 耗时、Trace Token 汇总；不将总耗时混同 Shell 截止时间 |
| 可观测性 | 缺失/未完结 Trace、导出延迟、缺失工具证据；单独标记，不伪造成通过 |

初次实验仅建立当前版本在统一 Flash 下的基线。此前模型池结果不能直接用于归因本次代码修复；后续比较应保持模型、数据集、配置和执行环境一致。

## 5. 当前限制

- 临时目录和独立 `user.home` 隔离测试数据与会话，不提供操作系统级 Shell 沙箱。
- Shell 自动放行规则尚未收紧，`always` 持久化也未实现，不纳入已完成能力。
- 单例冒烟与完整模型链路已验收，Opik 分数和输出已回读；原评分对输入及命令参数的精确保真覆盖不足，追加指标为 8/12，后续需定位修复后针对性复测。
- Opik 的 ClickHouse 与后端曾因 OOM 退出。经用户授权停止 5 个无关 AgentScope 容器后，已启动原 Opik 容器并完成数据集回读；未删除或重建数据库，正式测试前仍应检查服务状态。
