# 项目现状分析与后续开发规划

- 分析日期：2026-11-04。
- 分析基线：当前 `regnexe-cli` 0.1.0 源码、配置、测试、评测脚本及仓库文档。
- 状态：方向草案，具体实施过程、接口和验收用例后续逐项细化。
- 范围：区分当前已接入的能力、静态代码发现的问题，以及未来建议；不将框架历史设计或提案直接认定为当前实现。

## 1. 总体判断与产品定位

项目已经具备可用的终端 Agent 骨架：规划、工具执行、反思、会话持久化、任务恢复，以及 Skill、插件和 MCP 扩展。下一阶段应优先提升执行可靠性、自动化能力与可验证性，再扩展复杂任务和多 Agent 协作。

当前定位是基于 Java 的本地终端工作助手，面向代码与文件操作，通过 Skill 和 MCP 扩展其他任务。近期建议聚焦“面向 Java 项目与企业工具的可扩展终端 Agent”，先把以下场景做稳定：

- 分析 Maven、Spring 项目并定位代码与依赖问题。
- 根据需求修改代码，执行构建与测试并报告验证证据。
- 使用 Skill 固化团队开发流程。
- 使用 MCP 连接代码平台、工单和知识库。
- 中断后继续执行长任务，并明确恢复可能带来的副作用。

浏览器、办公文档、多模态与长期自主运行可逐步扩展，是否引入复杂编排应由实际任务成功率、耗时和成本决定。

## 2. 技术结构与职责边界

```text
用户输入 / 斜杠命令
        ↓
regnexe-cli
终端交互、配置、会话、权限确认、工具适配
        ↓
regnexe-agent 0.1.3
规划 → 执行 → 反思 → 下一轮 / 结束
        ↓
j-langchain
模型调用、工具调用、MCP 等基础能力
        ↓
文件系统 / Shell / 插件 / 外部服务
```

项目使用 Java 17、Spring Boot 3.2.12、JLine、SQLite 等技术，实际版本以 [pom.xml](../../pom.xml) 为准。

| 模块 | 当前职责 | 评价 |
|---|---|---|
| `CliMain` | 启动、REPL、Agent 构建、会话切换、插件与 MCP 命令 | 约 1,822 行，职责集中，是后续维护重点 |
| `config` | 模型、Agent 参数、工具、UI、Opik 配置 | 基本可用，缺少完整配置诊断 |
| `tools` | 文件、搜索、Shell、工作目录、MCP 适配 | 核心执行入口，需要优先强化可靠性 |
| `session` / `db` | 会话、对话记录、任务状态、数据库迁移 | 已有持久化设计和数据库回归测试 |
| `ui` | 主题、预览、确认、阶段与 Token 展示 | 已形成独立渲染层 |
| `event` / `observe` | 执行事件与 Opik 导出 | 支持排障与评测，仍可补充脱敏和治理 |
| `evals` | 数据集、运行器、规则与模型评分 | 已有雏形，尚未形成独立稳定的质量门禁 |
| `scripts` | 安装冒烟、发布打包 | 基础发布流程已具备 |

跨仓库职责建议保持明确：执行状态机、规划和反思归 `regnexe-agent`；模型协议和基础 MCP 能力归 `j-langchain`；终端产品与本地执行环境归 `regnexe-cli`。修改底层仓库时，要确认 CLI 实际使用的依赖产物与版本。

| 能力 | 当前实现 | 实际边界 |
|---|---|---|
| 交互式终端 | JLine REPL、输入历史、帮助、退出 | 主要面向人工交互 |
| Agent 执行闭环 | 接入规划、执行、反思和轮数限制 | 不能据此认定复杂任务成功率已验证 |

| 文件操作 | 读取、列表、文本搜索、创建、精确替换 | 缺少批量补丁、冲突检测和回滚 |
| Shell | 工作目录、确认、输出捕获、危险命令拦截 | 限制主要依靠启发式规则，超时存在缺陷 |

| 暂停 | Ctrl+C 请求暂停、二次中断退出 | 不代表底层操作都能立即取消 |
| 上下文管理 | 滑动窗口、摘要模型、会话压缩 | 主要按数量管理，缺少 Token 预算治理 |
| 项目记忆 | 加载用户和项目 `.rex/REX.md` | 静态规则注入，不是自动学习系统 |
| Skill | 发现、列表、直接斜杠调用 | 直接执行 Skill 不建立可恢复任务账本 |
| 插件 | 安装、卸载、启用、禁用，用户与项目作用域 | 配置冲突解释和来源追踪可增强 |
| MCP | 直接与插件配置、工具 schema 透传、调用确认 | 当前适配主要处理文本工具结果 |
| 可观测性 | 阶段事件、工具结果、Token 汇总、Opik | 缺少预算控制与统一脱敏策略 |

## 4. 优先处理的问题

以下结论来自静态代码核查，尚未通过专门的故障或攻击用例复现；后续修复应补充对应验证。

### 4.1 Shell 超时与取消

> 进展（2026-11-04）：本节描述的是分析时的旧实现。已完成异步输出读取、统一截止时间、暂停信号接入、中断标志恢复及已发现子进程清理，新增 8 项回归测试；实现与限制见[当天开发日志](../log/2026-11/2026-11-04.md)。后台命令与进程组隔离仍待后续设计。

分析时的 [BashTool](../../src/main/java/org/salt/regnexe/cli/tools/BashTool.java) 先阻塞读取输出直至 EOF，再执行带 30 秒超时的 `waitFor()`。命令持续运行或持有输出管道时，读取可能一直阻塞，超时逻辑无法及时到达。

建议异步读取输出，从启动时计算执行截止时间；超时或取消后终止进程及子进程，并保留部分输出。后续再扩展后台命令、轮询和长任务会话。

### 4.2 文件路径边界

> 进展（2026-11-04）：已统一读写真实路径校验、修复相对路径回退、校验新文件最近存在的父目录，并补充递归搜索与确认后写入的校验；新增 17 项回归测试。实现与剩余竞态限制见[当天开发日志第 4 节](../log/2026-11/2026-11-04.md#4-修复工作目录真实路径边界)。

分析时的 [WorkspaceContext.resolveForRead()](../../src/main/java/org/salt/regnexe/cli/tools/WorkspaceContext.java) 在相对路径查找失败后，直接回退到 `primaryRoot().resolve(candidate).normalize()`，没有重新验证根目录边界，包含 `../` 的路径可能越界。

读写路径主要通过 `normalize()` 和 `startsWith()` 做词法检查，尚未完整处理符号链接指向根目录外的情况。应统一路径策略，检查真实路径；创建文件时检查最近存在的父目录，并考虑检查与实际操作间的竞态。

### 4.3 Shell 自动放行规则

当前按命令前缀和少量字符串判断只读，覆盖不了命令参数和 Shell 语义：`git branch`、`git tag`、`git remote` 可修改状态，`find -exec` 可运行程序，以只读命令开头的复合命令也可能产生副作用。`mvn compile` 会写构建产物，还可能执行插件。

先收紧自动放行规则，保守处理复合命令，再评估文件系统、网络和进程层面的隔离。确认弹窗与字符串检查不能等同于操作系统沙箱。

### 4.4 恢复中的副作用与并发

恢复任务不保证工具只执行一次。建议建立工具调用 ID、参数摘要、执行状态、结果与副作用类型的记录，区分可重试读取、可核验写入及不可盲目重放的外部操作。对多进程恢复同一任务，应补充锁或租约。

具体采用哪种幂等或恢复协议，留待任务持久化专项设计确定。

### 4.5 评测工程整理

2026-11-05 复核：旧综合数据集 28 个用例已与 README 一致；评测源码、配置模板和数据集正常跟踪，虚拟环境、缓存及运行结果已忽略，当前没有被跟踪的评测编译缓存。这部分整理已完成。

按用户确认，现阶段继续使用 Opik 获取普通 Agent 用例的结果与工具证据，不优先建设单次执行入口、机器可读输出或独立本地结果协议。现有 `interactive_runner.py` 已通过真实 PTY、文件、SQLite 和进程检查完成交互验收，并保存本地 JSON 结果；无需为正常可用的评测链路增加额外架构。

后续重点放在用例覆盖、真实行为证据、失败原因分析和修改前后可比较的优化效果。保持测试脚本与当前 CLI 行为一致；评测采集或环境故障应结合已有日志识别，避免误当作模型能力退化。

## 6. 结构调整建议

采用渐进拆分，不重写整个项目：

```text
CliMain
├── CliApplication          启动、退出、资源生命周期
├── ReplLoop                输入循环、任务提交
├── SlashCommandRegistry    命令注册、路由
├── AgentFactory            Agent 装配
├── SessionService          会话、恢复
├── PluginService           插件安装、状态
└── McpConnectionManager    MCP 连接生命周期
```

新增跨模块职责建议：

- `PermissionService`：统一文件、Shell、MCP 授权策略。
- `ProcessExecutor`：统一进程超时、取消、输出、后台会话及退出状态。

复用已有 `CliRenderer` 与事件监听接口提供 JSON 输出。框架层负责规划解析恢复、任务状态机、检查点、完成证据、上下文预算与必要的子任务调度。

以上名称表示建议的职责划分，不是已确定的类名和包结构，后续设计时结合真实调用关系细化。

## 7. 分阶段路线

版本号仅用于讨论，不代表发布承诺；每阶段完成后依据验证结果调整下一阶段范围。

| 阶段 | 目标 | 主要交付 |
|---|---|---|
| `0.1.x` | 基础执行可靠 | 超时与取消、路径边界、只读规则、工具回归、评测目录整理 |
| `0.2` | 自动化与持续评测 | `rex exec`、JSON/JSONL、退出码、本地评测协议、CI |
| `0.3` | 代码任务闭环 | 多文件补丁、变更汇总、检查点、验证记录、后台命令 |
| `0.4` | 复杂任务可靠性 | 可编辑计划、Token/耗时预算、副作用治理，按需验证子任务 |
| 后续 | 扩展通用工作能力 | 浏览器、文档、多模态、外部系统、按需多 Agent |

### 阶段一：基础执行可靠

优先完成 Shell 超时、取消与子进程清理，文件边界校验，收紧自动放行，以及工具统一结果状态。为这些执行边界补充回归测试。

建议验收方向：无输出阻塞命令按时终止；拒绝授权后无副作用；相对路径与符号链接不能越过配置边界；取消、超时和执行失败能被调用方明确区分。

### 阶段二：自动化与持续评测

建议接口示意，尚未实现，参数和输出协议后续设计：

```bash
rex exec "修复测试失败" --output json
rex exec "分析当前项目" --output jsonl
```

输出至少包含任务 ID、状态、最终回答、工具结果摘要、验证结果、Token 与耗时。评测直接读取本地结构化结果，Opik 用于追踪和对比。

建立可重复基线，记录任务成功率、误报完成、恢复成功率、越界与授权错误、耗时和 Token。基础质量检查可离线运行，真实模型评测独立配置。

### 阶段三：代码任务闭环

增加精确补丁、多文件变更、文件版本检查、任务级变更汇总、显式检查点与撤销、构建测试结果记录，以及后台进程执行和轮询。避免覆盖用户同时修改的内容，明确验证已执行还是尚未执行。

### 阶段四：复杂任务与通用扩展

先验证现有多轮规划是否足够，再按实际瓶颈评估串行子任务与独立上下文；只有收益明确时才引入并行 Agent、工作树隔离与冲突合并。

历史上已决定不实施 coordinator/sub-task 重架构，见 [2026-07-10 开发日志](../log/2026-07-10-session-and-plan-perf.md)。本规划不推翻该决定，也不把子任务当作已确定需求。重新评估前，应先排查规划粒度、轮次预算与上下文问题，并提供基线对比。

## 8. 历史设计的使用原则

[Agent 改进方向](../design/02-agent-improvement.md) 是早期诊断，不能整体当作当前待办。空重定向与确认输入已有对应处理；历史日志也记录过规划解析重试、恢复计划、反思护栏和 `iterationsHint` 的落地。
